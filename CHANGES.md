# Changes

Notable changes, newest first: what someone running velox would notice (behaviour, performance,
API, defaults, fixes). The server embeds this file: `GET /version` lists the latest entries and
`GET /changes` returns it whole, so a node shows what its build contains.

Every PR to main that changes behaviour adds an entry at the top, in the PR itself:
`## YYYY-MM-DD · #PR · type: title` (the merge date, the PR number), then a few lines on what
changed and its measured effect. Hardware branches only tune kernels (`crates/velox-variant`) and
do not edit this file.

## 2026-11-25 · #37 · feat: build version and change log at `/version` and `/changes`
`GET /version` reports the commit, the ref it was built from, the build time and the latest
entries of this file; `/metrics` adds `velox_build_info{version,commit,ref}`; the startup line ends
with `velox 0.1.0+<commit> (<ref>, built …)`. Compare `commit` with `git ls-remote origin <ref>` to
check a deployment. Docker builds from a git URL need `BUILDKIT_CONTEXT_KEEP_GIT_DIR=1` to see the
commit (qwen-llm-inferencer's compose passes it); without it the commit reads `unknown`.

## 2026-11-25 · #31 · fix: NVML stalls no longer hold requests in the queue
Device-memory gauges are sampled on a `velox-mem` thread instead of the engine worker. Under WSL an
NVML call can stall for seconds (seen 5–106 s); the worker made one every second and on every
idle entry, so ~6% of back-to-back System One requests waited 1–5 s with the GPU idle. RTX 5090
rank50: p90 1.36 s / max 5.7 s → p99 276 ms / max 291 ms.

## 2026-11-23 · #30 · feat: reserved slots with idle leases
`POST /v1/slots/reserve|release`, `GET /v1/slots`: a token holds one lane (prefix kept warm,
compute priority while its request runs); a hold lapses 60 s after its last use. At most 3/4 of the
lanes can be held. Small buffers come from a stream-ordered pool (cudaMallocAsync): under WDDM
with a nearly full device, cudaMalloc/cudaFree had blocked the engine 0.3–2 s per image.

## 2026-11-22 · #28, #29 · perf: context-store eviction waits only for its own copies
Evicting or releasing a context-store entry waits for that entry's fences instead of a
device-wide synchronize (which waited out other lanes' prefill). RTX 5090 production evict p99
70 → 10 ms.

## 2026-11-21 · #26, #27 · feat: System One accepts llama.cpp's request form; two-letter rank ids
`/v1/systemone` also takes the llama.cpp-style body. Rank candidates are labelled with two-letter
ids, so keys are one token each.

## 2026-11-18 · #23 · fix: 2 × 128K context fits a 24 GB card
Warm-up aliasing, an admission reserve, and no CUDA graph instantiation after warm-up under WSL.

## 2026-11-17 · #22 · fix: pinned host memory stays within the context budget
Freed pieces coalesce and serve any size; before, a workload change could pin 7.7 GiB outside a
25.5 GiB arena in a day and push the host into swap.

## 2026-11-12 · #19, #20 · perf: System One multi-question batching
choice/noul/score answer many questions over one shared prompt, like rank: choice ×50 over a
5.3K-token state 20.3 s → 765 ms. (#21, question-after-criteria, was reverted: it broke lookups in
long numbered states.)

## 2026-11-11 · #18 · feat(qwen3-asr): quantized KV pool, fp8 by default

## 2026-11-09 · #16, #17 · feat: DSpine block drafter next to DFlash2
Batched rounds draft up to 15 tokens.

## 2026-11-06 · #1, #5, #6, #9 · feat: Qwen3-ASR-1.7B (`serve-asr`); disk context tier
`serve-asr` with fused batched decode, admission by request priority. The NVMe context tier keeps
only the most common prefix roots, for a fast cold start.
